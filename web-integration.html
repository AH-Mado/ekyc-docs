Front-end integration

A guide for front-end teams consuming the DIDC (Digital Identity & Digital Contract) web build.

It covers the postMessage protocol, the full message catalogue, the INIT payload, and the host-driven liveness hand-off.

info

All host ↔ DIDC communication happens over window.postMessage. Authentication for backend calls is handled by the session cookie set on the parent domain (DIDC's API requests go out with credentials: 'include'); no token is exchanged over the channel.

1

Message envelope

Every message — both directions — has the same shape:

JSON 
{ type: string, payload: object }
warning
Direction asymmetry — read carefully:
DirectionWire formatWhat to do
Host → DIDC A plain object { type, payload } (structured-clone) iframe.contentWindow.postMessage({ type, payload }, '*')
DIDC → Host A JSON-encoded string '{"type":"…","payload":{…}}' JSON.parse(event.data) before reading it

If you accidentally send a JSON string to DIDC, it will be silently ignored — DIDC only accepts objects from the host. The reverse is also true: the messages you receive are always strings, so always parse them.

ACKs

For every message DIDC receives, it posts an acknowledgement back:

JSON 
{ "type": "ACK_<ORIGINAL_TYPE>", "payload": {} }

For example, sending INIT produces an ACK_INIT. ACKs are delivery receipts — useful for logging and debugging, but you do not need to act on them.

2

The handshake — wait for LISTENING_READY before sending INIT

1
iframe loads, DIDC attaches its message listener
2
LISTENING_READY
3
INIT { headers, localization, metaData }
4
ACK_INIT
5
flow starts
6
(Location → eKYC scenes)

Do not send INIT on iframe.onload — DIDC's listener may not be attached yet. Always wait for LISTENING_READY. Only the first INIT is consumed; subsequent INIT messages are ignored.

3

The INIT payload

JavaScript 
{
  type: "INIT",
  payload: {
    headers: {
      version: "11111", // app/host version string
      language: "en", // "en" | "ar"
      platform: "web"
    },
    localization: { /* optional */ }, // key → string overrides; pass {} if none
    metaData: {
      serviceName: "INVESTMENT", // included in event payloads & API query params everywhere
      version: "V1", // included in API query params
      manualFlowAvailable: false // if false, "Continue manually" is hidden
    }
  }
}

Field reference

FieldRequiredNotes
headers.version yes Host app version; forwarded to the backend.
headers.language yes en or ar. Drives UI language.
headers.platform yes Always "web" from a browser host.
localization no Optional overrides for individual strings. Pass {} for defaults.
metaData.serviceName yes Service identifier (e.g. "INVESTMENT").
metaData.version yes Service version (e.g. "V1").
metaData.manualFlowAvailable yes Boolean. When false, the "Continue manually" CTA is hidden on every scene where it would otherwise appear.
info

Auth is not part of INIT. DIDC issues API requests with credentials: 'include' and relies on the session cookie set by the parent. The iframe must therefore be served from a domain that receives that cookie (same-site, SameSite=None; Secure).

info
Environment is no longer part of INIT.

It's baked into the DIDC build itself per deploy target — load the iframe URL that matches the environment you want (dev / test / staging / production). The host doesn't choose it at runtime.

4

Messages from DIDC → Host

Listen with a single window.addEventListener('message', …) and dispatch by type.

TypePayloadWhat it means / what to do
LISTENING_READY {} DIDC is ready. Reply with INIT.
START_LIVENESS {} Liveness check is starting — run your own face-capture UI on the host and reply with LIVENESS_ENDED. Full hand-off in §5.
UNAUTHORIZED {} A request returned 401. The parent's session cookie is invalid/expired — re-authenticate on the host side and reload the iframe.
CONTRACT_STATUS { status: "signed" | "notEligible" } Contract outcome.
CONTINUE_MANUAL {} User chose "Continue manually". Take them to your manual flow.
EXIT {} Flow finished or user exited. Tear down the iframe / navigate away. Not emitted when a terminal outcome (UNAUTHORIZED, CONTRACT_STATUS, CONTINUE_MANUAL) has already been sent in this session — that outcome is the end-of-flow signal and you should tear down the iframe on it directly.
ACTION_EVENT { event_name, ...params } Analytics passthrough. Forward to your analytics stack if you want it.
ACK_* {} Delivery receipt for a message you sent. Safe to ignore.

Unknown type strings are mapped to UNKNOWN internally and can be ignored.

5

The liveness hand-off

Liveness on web runs entirely in the host page — the host owns the camera and the face-detection logic. DIDC just hands off, waits for the captured images, then submits them to the backend.

1
START_LIVENESS {}
2
host runs its own face-capture UI, collects N images
3
LIVENESS_ENDED { type: "image", images: [{ challenge, buffer }, …] }
4
DIDC POSTs the result to: /api/v1/digital-identity/verify/id/liveness/multi
multipart body: face1, face2, … faceN (one part per captured image, in array order)

LIVENESS_ENDED payload

JavaScript 
{
  type: "image",
  images: [
    { challenge: "smile", buffer: <ArrayBuffer> }, // → face1
    { challenge: "right", buffer: <ArrayBuffer> }, // → face2
    { challenge: "left",  buffer: <ArrayBuffer> }, // → face3
    { challenge: "blink", buffer: <ArrayBuffer> }  // → face4
  ]
}
FieldTypeNotes
type "image" Reserved for future variants. Send "image" today.
images[i].buffer ArrayBuffer The raw image bytes. Uint8Array and base64 strings (including data: URLs) are also accepted, useful if you can't transfer binary.
images[i].challenge string Informational label (e.g. "smile", "right", "left", "blink"). DIDC logs but doesn't use it.
info
Array order matters.

The position in images becomes the multipart key: images[0] → face1, images[1] → face2, etc. The backend sees them in that order, so be deliberate about it.

warning
Challenge failed on your side?

Post LIVENESS_ENDED with an empty payload ({ type: "LIVENESS_ENDED", payload: {} }). DIDC treats that as a liveness failure, fires the standard analytics event, and routes the user to the same error screen used when the verify API rejects the submission. No need to invent your own error UX.
